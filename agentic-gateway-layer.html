§ 1

ארבע דרישות, ארבע שכבות תעבורה

השוק מוכר "AI Gateway" כמילה אחת, אבל מדובר בארבעה סוגי תעבורה שונים לחלוטין — עם מודלי סשן, אימות ומדידה שונים. זו הסיבה שרוב המוצרים חזקים בשתיים מהן וחלשים בשאר.

שער LLM

POST /v1/chat/completions · SSE · stateless

ניתוב בין ספקים, virtual keys, תקציבי טוקנים, semantic cache, guardrails ו‑failover. המדידה היא טוקנים ועלות, לא בקשות.

שער MCP

Streamable HTTP · OAuth 2.1 RS · stateful session

פדרציה של שרתי כלים, קטלוג ו‑discovery, הרשאה ברמת tool בודד, והגנה מפני tool poisoning ו‑rug pull. סשנים ארוכי חיים ודו‑כיווניים.

שער A2A

JSON-RPC · Agent Card · task lifecycle

גילוי סוכנים, האצלת זהות עם שרשרת token exchange ניתנת למעקב, ו‑audit מלא של שיחות בין סוכנים. הפרוטוקול הצעיר מהשלושה.

API Management

OpenAPI · dev portal · lifecycle · plans

קטלוג, פורטל מפתחים, מחזור חיים, מכסות, מוניטיזציה וממשל. הדרישה הוותיקה — וזו שהכי הרבה מוצרי AI‑native מפספסים.

§ 2

הארכיטקטורה המוצעת

data plane אחד לכל תעבורת ה‑AI, מאחורי חוזים סטנדרטיים בלבד. כל רכיב בתרשים ניתן להחלפה מבלי לגעת בקוד של האפליקציות.

§ 3

מפת המוצרים

השוק מתחלק לשלושה ארכיטיפים. ההבדל ביניהם הוא לא רשימת פיצ'רים אלא מאיזה כיוון הם הגיעו — וזה קובע במה הם טובים באמת.

A · AI-native agent gateways

agentgateway

Linux Foundation · נתרם ע"י Solo.io Apache-2.0

פרוקסי שנבנה מאפס לתעבורה אגנטית: MCP ו‑A2A כאזרחים מדרגה ראשונה, ניתוב LLM ל‑OpenAI, Anthropic, Gemini ו‑Bedrock מאחורי API תואם‑OpenAI אחד, פדרציה ו‑multiplexing של שרתי MCP, RBAC עם מנוע מדיניות CEL, JWT, rate limiting ו‑OpenTelemetry. תומך ב‑Kubernetes Gateway API מלא (HTTPRoute, GRPCRoute) וגם רץ כבינארי בודד.

הפתרון היחיד שנבנה סביב סשנים stateful ודו‑כיווניים במקום להוסיף אותם לפרוקסי REST. ממשל ניטרלי מוריד סיכון נעילה. תמיכה מסחרית זמינה דרך Solo Enterprise.

kgateway

CNCF Sandbox · Solo.io Apache-2.0 Portal ב‑EE

שער API מבוסס Envoy עם שבע שנות פרודקשן מאחוריו. נותן את כל צד ה‑REST/gRPC — ניתוב, mTLS, JWT, circuit breakers, rate limiting — ומשתלב ישירות עם agentgateway. Solo Enterprise מוסיף פורטל מפתחים, אנליטיקה ומוניטיזציה, WAF, DLP, external auth, תמונות FIPS ותמיכה 24×7.

זה מה שהופך את הזוג הזה מ"שער AI" ל"גם APIM". הפורטל והמוניטיזציה פחות עמוקים מ‑Kong או Gravitee — מספיק לארגון שמתחיל APIM מאפס, פחות מספיק לקטלוג של מאות APIs עם שותפים חיצוניים.

ContextForge

IBM · mcp-context-forge Apache-2.0

רג'יסטרי ופרוקסי שמאחד MCP, A2A ו‑REST/gRPC לנקודת קצה אחת עם discovery מרכזי, RBAC וצוותים, OAuth 2.0/OIDC/SSO, token exchange לפי RFC 8693, אחזור credentials פר‑משתמש מ‑Vault, המרת OpenAPI לסכמות כלי MCP, ו‑40+ תוספים. הגיע ל‑GA במאי 2026 וממשיך בקצב מהיר.

לא שער תעבורה ולא APIM — אבל הקטלוג והממשל הכי בשלים בקטגוריה לשרתי MCP וסוכנים. שווה לשקול אותו לצד השער כשכבת רישום, לא במקומו.

B · APIM platforms adding AI

Gravitee Platform

Gravitee.io CE: Apache-2.0 AI: EE בלבד

הספק היחיד שמאגד LLM Proxy, MCP Proxy ו‑A2A Proxy תחת חוויית ניהול אחת, מעל פלטפורמת APIM מלאה: גייטוויי, פורטל, קטלוג, פדרציה של שערים אחרים, ניהול אירועים ל‑Kafka וניהול הרשאות. Traces של OpenTelemetry מועשרים במזהי ישויות מהקטלוג ובהחלטות מדיניות. SaaS, self‑hosted או היברידי.

המועמד החזק ביותר אם עומק ה‑APIM שווה בחשיבותו לצד ה‑AI — control plane אחד, ספק אחד, חוזה אחד. המחיר: כל יכולות ה‑AI נעולות מאחורי Enterprise Edition, וזה בדיוק החלק שקשה להחליף אחר כך.

Kong AI Gateway

Kong Inc. · Konnect Core: Apache-2.0 AI: Enterprise

Agent Gateway הושק באפריל 2026 בגרסה 3.14 והוסיף תעבורת A2A עם spans ייעודיים ב‑tracing, audit מלא של שיחות בין סוכנים ומעקב צריכת טוקנים גרנולרי, לצד ai-mcp-proxy (מגרסה 3.12) שממיר REST ל‑MCP ומתווך לשרתי MCP קיימים. MCP Composer ו‑MCP Runner בדרך.

הבשל ביותר ב‑A2A והאקוסיסטם הגדול ביותר. אבל ai-mcp-proxy ותוספי ה‑AI המתקדמים הם Enterprise בלבד, ו‑Konnect מכוון ל‑SaaS — שתי נקודות שמושכות לכיוון נעילה.

WSO2 API Platform

WSO2 Apache-2.0

הושק במרץ 2026: AI Gateway שהופך APIs קיימים לכלי MCP וממשל על שימוש בכלי MCP של צד שלישי, AI Workspace כ‑control plane ל‑LLMs ושרתי MCP עם 30+ guardrails, מדיניות מודעת‑טוקנים, מוניטיזציה מאוחדת, ופדרציה של שערים קיימים כמו Kong ו‑Azure APIM ללא הגירה.

הבסיס הכי רחב שפתוח ב‑Apache‑2.0, והפדרציה מעניינת לארגון עם עבר. פחות מפורש לגבי A2A מהשניים שמעליו, וה‑stack כבד יותר לתפעול.

C · LLM-first gateways

LiteLLM

BerriAI OSS core

ביוני 2026 הפך OCI Generative AI לספק native ב‑LiteLLM — כולל חתימת OCI Signature v1 לכל מסלולי האימות: credentials ידניים, משתני סביבה, OCI SDK Signer, Instance Principal ו‑OKE Workload Identity. Oracle עצמה מציבה את LiteLLM כשער ה‑AI הארגוני על OCI: virtual keys, תקציבים, ניתוב, cache, guardrails ו‑audit.

זו העובדה הכי שימושית במסמך הזה. גם אם לא בוחרים ב‑LiteLLM כשער הראשי — זה הרכיב שמובטח שיעבוד מול OCI ביום ההגירה, ושווה כתוכנית מגירה לשכבת ה‑LLM.

Envoy AI Gateway · Apache APISIX · Tyk · Apigee · Zuplo

שאר הזירה מעורב

לכולם יש שער LLM וברובם גם יכולת MCP כלשהי. אף אחד מהם לא מספק A2A נכון להיום. Apigee בולט ביכולת לייצר שרתי MCP אוטומטית מ‑OpenAPI קיים — אבל הוא Google Cloud בלבד, מה שפוסל אותו כשהיעד הוא Oracle.

לא רלוונטיים כשער מאוחד. Envoy AI Gateway ו‑APISIX נשארים רלוונטיים כתוכנית ב' אם הליבה הנבחרת תיתקע.

§ 5

ההחלטה

בהינתן שאין APIM קיים, שהעדפת הרישוי היא OSS עם חוזה תמיכה, ושה‑Kubernetes בשל ובפרודקשן — זו הקומבינציה שנותנת את הכיסוי הרחב ביותר עם עלות הפרידה הנמוכה ביותר.

AI data plane agentgateway MCP, A2A וניתוב LLM בשער אחד. Apache‑2.0 תחת Linux Foundation — לא תחת ספק.
API data plane + portal kgateway Envoy בוגר, Gateway API תקני, Gloo Portal ב‑Enterprise. זה ה‑APIM הראשון של הארגון.
Tool & agent registry ContextForge קטלוג MCP/A2A, בעלות על כלים לפי צוות, ו‑token exchange לפי RFC 8693 מול Vault.
Fallback · LLM LiteLLM ספק OCI native מיוני 2026, כולל OKE Workload Identity. ביטוח ליום ההגירה.
Commercial cover Solo Enterprise 24×7, תמיכה N‑3, תמונות FIPS, WAF ו‑DLP — מעל אותה ליבת קוד פתוח.
אם ההעדפה תשתנה Gravitee EE אם ועדת הארכיטקטורה תעדיף ספק אחד וחוזה אחד על פני גמישות — זו החלופה, ולא Kong.

חמישה חוזים שאסור להפר

ההחלטה על מוצר היא הפיכה. ההחלטה על חוזי הממשק — לא. אלה הכללים שהופכים את כל השאר לניתן להחלפה, ובדיוק הם שמכשירים את הקרקע ל‑OCI.

חוזה LLM צפוני אפליקציות מדברות רק POST /v1/chat/completions תואם‑OpenAI. זהו בדיוק הפורמט ש‑OCI Generative AI חושפת נייטיב ב‑/openai/v1 — כולל Responses ו‑Conversations. אף SDK ספציפי‑ספק בקוד האפליקציה.
MCP רק מרוחק Streamable HTTP בלבד, לעולם לא stdio בפרודקשן. כל שרת MCP הוא OAuth 2.1 Resource Server עם audience מוגדר. זה מה שמאפשר לשער לאכוף הרשאה ברמת כלי בודד.
Agent Cards בבעלותנו רג'יסטרי A2A שהארגון מחזיק, לא רג'יסטרי מוטמע בפלטפורמת ספק. Oracle השיקה ביולי 2026 A2A Server בתוך Autonomous AI Database — הוא ייכנס כמקור נוסף לרג'יסטרי שלנו, לא כרג'יסטרי עצמו.
תצורה כ‑Gateway API כל הניתוב מוגדר ב‑CRDs תקניים של Kubernetes Gateway API תחת GitOps. CRD ייחודי לספק הוא חוב שצריך אישור מפורש.
טלמטריה וזהות תקניות OTLP החוצה בלבד — יופנה ל‑OCI APM ביום ההגירה. זהות דרך OIDC בלבד — תוחלף ל‑OCI IAM domains. שני חיבורים, לא מאה.
§ 6

מה Oracle באמת נותנת בעוד שנה

זו הבדיקה החשובה, והתשובה מפתיעה: Oracle בונה נקודות קצה אגנטיות ופלטפורמת סוכנים מנוהלת — אבל לא שער ניטרלי לתעבורת AI של צד שלישי. אין ב‑OCI מוצר שיחליף את השכבה הזו.

GAP

OCI API Gateway

JWT, rate limiting, CORS, usage plans ומוניטיזציה — שער קל משקל ותו לא. ארכיטקטורת הייחוס של Oracle ל‑API Management למודלי AI מרכיבה אותו יחד עם Vault, Functions ו‑Cache with Redis. אין פורטל מפתחים, אין מדידת טוקנים, אין MCP ואין A2A.

PARTIAL

OCI Enterprise AI

הגיע ל‑GA וכולל model router, אורקסטרציה של סוכנים, guardrails, audit logs בלתי ניתנים לשינוי, אפשרויות sovereign ו‑zero data retention. מצוין — אבל עבור סוכנים שרצים בתוך OCI, לא כשכבת ממשל רוחבית מעל כל תעבורת ה‑AI של הארגון.

FITS

GenAI · OpenAI-compatible

inference.generativeai.{region}.oci.oraclecloud.com/openai/v1 עם /responses, /conversations, /chat/completions, /vector_stores ו‑/containers, ואימות דרך OCI IAM. ה‑Responses API אף מקבל כלי מסוג mcp עם server_url ישירות.

PARTIAL

שרתי MCP מנוהלים

SQLcl, OCI Database Tools (serverless מנוהל), ORDS עם endpoint /mcp, MySQL, ואוסף שרתי OCI ל‑Cloud Guard, Compute, Storage, IAM וניטור. אלה שרתי MCP מעולים — כלומר יעדים שיישבו מאחורי השער שלנו.

PARTIAL

Autonomous AI DB · A2A Server

הוכרז ביולי 2026: יכולת multi-tenant מנוהלת בתוך בסיס הנתונים לגילוי והפעלה של סוכנים, עם הרשאה נייטיבית, לוגים, rate limiting ואכיפת מדיניות. מצוין לסוכנים שחיים ליד הדאטה — אבל קשור ל‑ADB ולא מכסה סוכנים חיצוניים.

FITS

OKE

כל המועמדים שנבחרו הם עומסי עבודה סטנדרטיים של Kubernetes. ההגירה היא Helm charts, OCI Vault במקום הסוד הנוכחי, OCI Load Balancer, ו‑OKE Workload Identity לאימות מול שירותי OCI. אין שכתוב אפליקציות.

§ 7

סיכונים ומה עושים איתם

A2A הוא הפרוטוקול הצעיר — ושם הכי קל להיתקע

הבשלות בין המוצרים לא אחידה: Kong טוען לכיסוי הרחב ביותר, Gravitee ו‑agentgateway מספקים proxy מלא, ורוב הזירה לא מספקת כלום.

מיטיגציה: להתחיל A2A רק בין סוכנים פנימיים, להחזיק את ה‑Agent Cards ברג'יסטרי שלנו, ולא לחשוף A2A לשותפים חיצוניים לפני שהפרוטוקול מתייצב.

פערי APIM מול פלטפורמה בוגרת

kgateway + Gloo Portal נותנים גייטוויי, פורטל, אנליטיקה ומוניטיזציה — אבל לא ממשל מחזור חיים בעומק של Gravitee, Kong או Axway.

מיטיגציה: להגדיר מראש את סף הכאב — מספר APIs, מספר צרכנים חיצוניים, דרישת מוניטיזציה. אם חוצים אותו, החלופה היא Gravitee, והחוזים מ‑§5 הופכים את המעבר לטכני בלבד.

יכולות AI נעולות מאחורי Enterprise

אצל Kong וגם Gravitee דווקא יכולות ה‑MCP וה‑A2A הן EE בלבד — כלומר החלק הקריטי הוא החלק שאי אפשר להריץ בלי רישיון.

מיטיגציה: זו הסיבה המרכזית להמלצה. ב‑agentgateway ו‑kgateway כל יכולות התעבורה בליבה ה‑Apache‑2.0; הרישיון קונה תמיכה ו‑hardening, לא את היכולת לעבוד.

זמינות מודלים ואזורים ב‑OCI

נקודות הקצה תואמות‑OpenAI תומכות רק במודלים נתמכים באזורים נתמכים — מה שעלול לא לכסות את כל מה שרץ היום.

מיטיגציה: למפות כבר עכשיו את המודלים בשימוש מול מטריצת האזורים של Oracle, ולהשאיר את השער מסוגל לנתב לשני ספקים במקביל גם אחרי ההגירה.

§ 8

תוכנית 90 יום

לא POC של פיצ'רים — POC של חוזים. כל שלב מסתיים בשער החלטה שאפשר לענות עליו בכן או לא.

יום 1–20

שכבת LLM בלבד

  • agentgateway על ה‑K8s הקיים, מול שני ספקי LLM בפרודקשן
  • אכיפת החוזה: כל צרכן עובר ל‑/v1/chat/completions, אפס SDK ספציפי‑ספק
  • virtual keys לכל צוות, תקציבי טוקנים, OTLP ל‑stack הניטור הקיים
  • במקביל: הרצת LiteLLM מול OCI GenAI בטננסי ניסיון לאימות מסלול ההגירה

שער: האם 100% מתעבורת ה‑LLM עוברת בשער, ויש דוח עלות לפי צוות?

יום 21–50

MCP וקטלוג הכלים

  • ContextForge כרג'יסטרי; שלושה עד חמישה שרתי MCP פנימיים בעלי ערך אמיתי
  • הסבת כל שרת ל‑Streamable HTTP + OAuth 2.1, ביטול stdio
  • הרשאה ברמת כלי בודד לפי צוות, ובדיקת tool poisoning ו‑rug pull
  • token exchange מול Vault לזהות משתמש‑קצה אל מול מערכות המקור

שער: האם אפשר לענות "מי הפעיל איזה כלי, בשם מי, ומתי" מלוג אחד?

יום 51–75

A2A ו‑APIM במקביל

  • שני סוכנים פנימיים מדברים A2A דרך השער, עם audit מלא של השיחה
